# 2032 — Exporter Register

**Status: PROPOSED FOR REVIEW. NOT applied to production.**

## What this migration does
Adds the schema needed for the Exporter Register feature (Exporters, under
Licensing & Permits, directly below Agencies):

- 1 new nullable column on `certificate` (`disputedCounty`) — additive
  only. An Exporter's own license record is a regular `certificate` row
  with `permitOrLicenceType = 'EXPORTER'`, reusing every column the 2028
  Local Produce Buyer and 2029/2030 Agency migrations already added
  (`verificationToken`, `buyerDisplayName`, `county`, `isPubliclyBlocked`,
  `publicBlockReason`, `stagedPermitNumber`, `sourceRecordId`,
  `isHistoricalImport`, `importRawData`, `logoUrl`) — no new column was
  needed for those. `disputedCounty` is the one genuinely new concept:
  it preserves a second, disputed county value for a record under staff
  review (currently only Meridian Commodity Inc.) without ever discarding
  either candidate.
- One new table: `exporter_import_run` (audit trail of every preview/apply
  import run, mirroring `local_produce_buyer_import_run` and
  `agency_import_run`).
- No existing column is altered or dropped; all existing rows remain valid
  with the new `certificate.disputedCounty` column at its default (NULL).

This file was generated by diffing the schema TypeORM's `synchronize: true`
produced on a **disposable copy** of the local staging database
(`eudr_migration_test_2032`, created via `createdb -T eudr_db`) against the
pre-migration schema — `DB_SYNCHRONIZE=false` was set before this file
itself was tested against that copy, so the real `eudr_db` staging database
is never auto-synchronized by this feature's development.

## What this migration deliberately does NOT do
- It does **not** run the 12-record historical Exporter import. That is a
  separate, explicit, idempotent, ADMIN-only application action
  (`ExporterImportService.apply()` / `POST /api/exporters/import/apply`),
  gated on staff reviewing the dry-run reconciliation report first —
  exactly the same review gate used for the 2028 Local Produce Buyer and
  2029 Agency imports. Folding the import into a schema migration would
  remove that review step.
- It does not touch any table/column outside this feature's scope.
- It does **not** distinguish Local vs. Foreign exporters in the register
  itself. `Application.category` already has separate `LOCAL_EXPORTER` /
  `FOREIGN_EXPORTER` enum values (pre-existing, used by the live /apply
  wizard), but the Exporter Register's own table/filters have no
  Local/Foreign column per the spec — every historical-import row is
  created under `ApplicationCategory.LOCAL_EXPORTER` with a single,
  unified `permitOrLicenceType = 'EXPORTER'` certificate discriminator,
  exactly mirroring how the register was specified (Company Name, County,
  Export License Number, Issued, Expires, Status, Download QR — no
  Local/Foreign column).

## Meridian Commodity Inc. (MCI) — county conflict
The batch-level overview lists Montserrado county for every record; this
exporter's own historical QR says Nimba County instead. Per the approved
decision:
- The record imports with `isPubliclyBlocked = true` — its public QR is
  **disabled** (no `verificationToken` issued) until staff confirm the
  correct county.
- **Both** candidate values are preserved: `certificate.county` holds the
  overview's Montserrado value, `certificate.disputedCounty` holds the
  historical QR's Nimba value.
- The license number itself (`LACRA-EXP-044-2026`) is NOT in conflict and
  is set normally as `certificateNumber` — only the county is held for
  review.
- Staff resolve this via `PATCH /api/exporters/:id/resolve-conflict`
  (`ExporterController.resolveConflict`), which accepts an optional
  corrected `county`, clears `isPubliclyBlocked`, and issues a fresh
  `verificationToken` — `disputedCounty` is left in place afterward as a
  permanent audit record of the alternate value that was considered.

## License number formatting — preserved verbatim
Per the explicit instruction, every license number in the seed data is
preserved exactly as provided, including:
- Leading zeros: `LACRA-EXP-030-2026`, `LACRA-EXPO-033-2026`,
  `LACRA-EXP-037-2026`, `LACRA-EXP-044-2026` (3-digit) vs. `LACRA-EXP-01-2026`,
  `LACRA-EXP-06-2026`, etc. (2-digit, no leading zero beyond the single
  digit).
- The unique `EXPO` (not `EXP`) prefix on Substantial Trade Group of
  Companies's license (`LACRA-EXPO-033-2026`) — every other record uses
  `EXP`.
License numbers are stored and matched as exact strings (`certificateNumber`
is a plain `character varying` column) — never parsed as integers or
re-padded.
