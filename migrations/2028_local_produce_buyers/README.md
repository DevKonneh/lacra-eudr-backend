# 2028 — Local Produce Buyer Register

**Status: PROPOSED FOR REVIEW. NOT applied to production.**

## What this migration does
Adds the schema needed for the Local Produce Buyer Register feature:

- 12 new nullable columns on `certificate` (verification token, buyer
  display fields, public-block flags, historical-import provenance,
  renewal/agency self-references). No existing column is altered or
  dropped; all existing rows remain valid with these columns `NULL`.
- Two new tables: `local_produce_buyer_sequence` (single-row atomic
  counter for the non-year-resetting `LACRA-###-YYYY` numbering) and
  `local_produce_buyer_import_run` (audit trail of every
  preview/apply import run).
- Two new UNIQUE constraints (`verificationToken`, `sourceRecordId`) and
  two new self-referencing foreign keys (`predecessorCertificateId`,
  `agencyCertificateId`).
- The pre-existing UNIQUE constraint on `certificateNumber` is **left
  untouched** — not relaxed, per the approved decision.

This file was generated by diffing the schema TypeORM's `synchronize: true`
produced in local staging (`eudr_db`) against the pre-migration schema, so
`up.sql` is a faithful, already-verified-working reproduction of what was
tested in Phase 2's staging pass (see the staging test results shared
alongside this migration).

## What this migration deliberately does NOT do
- It does **not** run the 83-record historical import. That is a separate,
  explicit, idempotent, ADMIN-only application action
  (`LocalProduceBuyerImportService.apply()` /
  `POST /api/local-produce-buyers/import/apply`), gated on staff reviewing
  the dry-run reconciliation report first. Folding the import into a schema
  migration would remove that review step.
- It does not touch any table/column outside this feature's scope
  (`application`, `application_status_history`, etc. are read/written by
  application code, not migrated here, since no new columns were added to
  them — the historical import reuses their existing columns, e.g.
  `application.category = 'LOCAL_BUYER'`, `action = 'HISTORICAL_IMPORT'`).

## Status computation semantics (for migration reviewers)
The public/admin "VALID" vs "EXPIRED" status is computed live by
`PermitVerificationService.computePublicStatus()` (used identically by both
public verification routes), not stored as a column. Reviewers approving
this migration should know the exact rule, since it directly affects when a
permit holder's QR stops showing Valid:

> **A permit becomes Expired at 00:00 Liberia time on its listed
> expiration date.** The expiration date itself is the first Expired day —
> it is NOT the last valid day. The last valid day is the calendar day
> immediately before the recorded `expiryDate`.

This was verified with two separate, independent tests on a real record
(A. Quiah Nelson, LACRA-194-2026) with Liberia's calendar date at
2026-11-07 at test time:
- `expiryDate` set to 2026-11-08 (the day after today) → live status
  `VALID`.
- `expiryDate` set to 2026-11-07 (today, i.e. the expiration date itself)
  → live status `EXPIRED`.
Both results were confirmed directly against the public verification API
and by rendering the actual public verify page in a browser (screenshots
retained). The record's `expiryDate` was restored to its original value
immediately afterward.

**Update — comment corrected:** the inline comment directly above the
`>=` comparison in `computePublicStatus()` previously read "the
expiration date itself is the last valid day," which described the
opposite of what the `>=` comparison actually does. This has now been
fixed in `src/services/PermitVerificationService.ts` — the comment text
now states the rule correctly (expiration date = first Expired day, not
the last valid day). **Only the comment was changed; the underlying
`>=` comparison itself was left exactly as-is**, so the tested behavior
above (confirmed again in this phase's retest, see below) is unchanged.
Verified with `npx tsc --noEmit` (0 errors) immediately after the edit,
confirming this was a comment-only change.

## Safeguards added (this phase) — code-level, not just documentation

The duplication/blank-permit-number risk described below (discovered and
originally only *documented* in the prior review pass) has now been
**closed with three independent, defense-in-depth guards** implemented
directly in source. All three were implemented, type-checked
(`npx tsc --noEmit`, 0 errors), and retested end-to-end on disposable
databases (results below). **No commits, pushes, or production changes
have been made — this is all still local, uncommitted, pending review,**
exactly as instructed.

### Guard 1 — `down.sql` refuses to run if any Local Produce Buyer records exist

`down.sql` now opens with a PL/pgSQL pre-flight check, run inside the same
transaction as the destructive statements:

```sql
BEGIN;

DO $$
DECLARE
    buyer_count integer;
BEGIN
    IF to_regclass('public.certificate') IS NOT NULL THEN
        SELECT COUNT(*) INTO buyer_count
        FROM certificate
        WHERE "permitOrLicenceType" = 'LOCAL_BUYER';

        IF buyer_count > 0 THEN
            RAISE EXCEPTION
                'Refusing to run down.sql: % certificate row(s) with permitOrLicenceType = ''LOCAL_BUYER'' already exist (imported and/or issued). ... See migrations/2028_local_produce_buyers/README.md, "How to restore the lost values", before proceeding.',
                buyer_count;
        END IF;
    END IF;
END $$;

-- ... the original DROP TABLE / ALTER TABLE statements, unchanged ...

COMMIT;
```

**How it works:** `RAISE EXCEPTION` inside a `DO` block aborts the entire
enclosing transaction — every statement after it (including all the
`DROP TABLE`/`ALTER TABLE` statements) never takes effect, and the
`COMMIT;` at the end becomes a no-op on an already-aborted transaction
(Postgres reports it as a rollback). `to_regclass('public.certificate')`
makes the check itself safe to run even in an environment where `up.sql`
was never applied (the `certificate` table check is skipped if the table
somehow doesn't exist, rather than erroring).

**What staff should do if this guard fires:** it means Local Produce Buyer
records already exist in this database — running `down.sql` would
silently destroy their QR tokens, hold flags, and import identities (see
"What is lost" below) with no way to resume cleanly. Follow **"How to
restore the lost values"** below (export the 12 columns first, then
rollback, then restore from the export) rather than attempting to bypass
this guard.

**Tested:** ran `down.sql` directly via `psql -f` against a disposable
database populated with all 83 imported records. Confirmed the exception
fires with the exact row count (83), every subsequent statement in the
file reports "current transaction is aborted, commands ignored until end
of transaction block," and a post-check confirms the schema (all 12
columns, both new tables, both constraints) is completely unchanged
afterward.

### Guard 2 — the import refuses to run if it detects a prior import's orphaned rows

A new error class and pre-flight check were added to
`LocalProduceBuyerImportService`:

```typescript
export class LocalProduceBuyerImportIntegrityError extends Error {
    constructor(public readonly orphanedCount: number) {
        super(`Refusing to proceed: ${orphanedCount} existing "LOCAL_BUYER" certificate record(s) have no sourceRecordId. ...`);
        this.name = "LocalProduceBuyerImportIntegrityError";
    }
}

// Detects the signature of a prior import whose idempotency key
// (sourceRecordId) was lost — e.g. by a schema rollback run without first
// exporting/restoring the dropped columns. Uses Application.submissionMethod
// = "Historical Register Import" as a secondary signal that survives a
// certificate-column rollback, so legitimate live LOCAL_BUYER issuances
// (which never have that submissionMethod, and legitimately have no
// sourceRecordId) are never false-flagged.
private static async assertNoOrphanedImports(manager): Promise<void> {
    const orphanedCount = await manager
        .getRepository(Certificate)
        .createQueryBuilder("cert")
        .innerJoin(Application, "app", "app.id = cert.applicationId")
        .where("cert.permitOrLicenceType = :type", { type: "LOCAL_BUYER" })
        .andWhere("app.submissionMethod = :method", { method: "Historical Register Import" })
        .andWhere("cert.sourceRecordId IS NULL")
        .getCount();

    if (orphanedCount > 0) {
        throw new LocalProduceBuyerImportIntegrityError(orphanedCount);
    }
}
```

Called as the **first operation** in both `preview()` (against
`AppDataSource` directly) and `apply()` (inside the transaction, against
the transactional `manager`, before any repository is even obtained) — so
neither the dry-run report nor the real write path can proceed past an
orphaned-row state.

`LocalProduceBuyerController.previewImport()` and `applyImport()` now
catch `LocalProduceBuyerImportIntegrityError` specifically and return
**HTTP 409 Conflict** with the error's descriptive message (instead of
falling through to a generic 500), so the admin UI can surface this as an
actionable, distinct condition rather than an unexplained server error.

**What staff should do if this guard fires (409 response):** it means some
existing `LOCAL_BUYER` certificates were created by a prior historical
import but have since lost their `sourceRecordId` — almost always the
result of a `down.sql` rollback that ran without first exporting/restoring
the dropped columns. Do **not** proceed with preview/apply until the
orphaned rows are resolved: either restore their `sourceRecordId` from a
backup (see restore procedure below) or have staff explicitly review and
manually remove/reconcile them. Proceeding without resolving this would
create a second, duplicate set of records for buyers who may already have
one — exactly the 166-row duplication bug this guard exists to prevent.

**Tested:** against a freshly-populated disposable database (83 records,
78 added / 5 held), manually stripped `sourceRecordId` from 3 of the 83
rows (simulating a partial/corrupted rollback). Confirmed both `preview()`
and `apply()` throw `LocalProduceBuyerImportIntegrityError` citing "3
existing LOCAL_BUYER certificate record(s) have no sourceRecordId," and
confirmed the certificate row count was unchanged (83 before the attempted
`apply()` call, 83 after) — proving the transaction aborts cleanly with
zero writes rather than partially applying.

### Guard 3 — public verification refuses any record without an issued permit number

A new exported function in `PermitVerificationService.ts`:

```typescript
export function hasIssuedPermitNumber(certificate: Certificate): boolean {
    return !!certificate.certificateNumber && certificate.certificateNumber.trim().length > 0;
}
```

is now checked, **in addition to** the existing `isPubliclyBlocked` check,
in both public-facing verification routes:

- `PermitVerificationController.verifyByToken()` (the QR-code route):
  ```typescript
  if (!certificate || certificate.isPubliclyBlocked || !hasIssuedPermitNumber(certificate)) {
      return res.status(404).json({ success: false, message: "This permit could not be verified. The QR code may be invalid or the record is not yet published." });
  }
  ```
- `ApplicationController.verifyCertificate()` (the certificate-number
  route):
  ```typescript
  if (certificate.isPubliclyBlocked || !hasIssuedPermitNumber(certificate)) {
      return errorResponse(res, "Certificate not found. This certificate number could not be verified.", [], 404);
  }
  ```

Both routes return the **same 404 response shape** used for "not found" —
no new distinguishable response was added for this case, preserving the
existing "never reveal why a record didn't resolve" design for
unauthenticated callers.

This closes the exact hole discovered in the prior review's duplication
test: a record can end up with a live, non-held `verificationToken` but a
blank/null `certificateNumber` (the state a naive post-import rollback and
re-import produces for non-held buyers, since the conflict-detection logic
only flags true shared-number conflicts from the source data, not
accidental collisions with leftover orphaned rows). Without this guard,
scanning such a record's QR would return a "valid-looking" response with
an empty permit number to the public.

**Tested** against a freshly-populated disposable database (83 records):
took a healthy, non-held, successfully-imported record (A. Quiah Nelson,
originally `certificateNumber = LACRA-194-2026`) and directly corrupted it
to reproduce the bug state — first with `certificateNumber = NULL`, then
separately with `certificateNumber = ''` (empty string) — while leaving
its `verificationToken` live and `isPubliclyBlocked = false` unchanged in
both cases. Then actually invoked the real controller methods
(`PermitVerificationController.verifyByToken()` and
`ApplicationController.verifyCertificate()`) against mock
request/response objects pointed at the disposable database (not just the
bare `hasIssuedPermitNumber()` boolean in isolation):

| Scenario | Route | Result |
|---|---|---|
| Live token, `certificateNumber = NULL` | `verifyByToken()` | **404**, generic message, no permit number in response |
| Live token, `certificateNumber = ''` | `verifyCertificate()` | **404**, generic message |
| Control: healthy, untouched record (Aaron Dahn) | `verifyByToken()` | **200**, correct permit number (`LACRA-237-2026`) returned |

The control case confirms the guard does not over-block legitimate
records — only the specific "token present, no real permit number" state
is refused.

## Rollback

`down.sql` reverses the schema changes only: it drops the two new tables
(`local_produce_buyer_sequence`, `local_produce_buyer_import_run`) and the
12 new `certificate` columns/constraints added by `up.sql`. It does **not**
delete any `Application`/`Certificate` rows — those rows survive, but with
all Local Produce Buyer-specific data permanently gone from them (dropped
columns cannot be recovered by re-adding the column; the values are gone).

**As of this phase, `down.sql` will refuse to run at all (see Guard 1
above) if any `LOCAL_BUYER` certificate rows exist** — so the scenario
described in this section ("what is lost if down.sql runs after the
import") can now only happen if someone deliberately bypasses the guard
(e.g. by manually deleting the `LOCAL_BUYER` rows first, or editing
`down.sql` itself). It remains documented in full below because
understanding exactly what the guard is protecting against is essential
context for anyone reviewing or ever needing to bypass it deliberately.

### What is lost if `down.sql` runs after the import has been applied

Tested directly (apply import → `down.sql` → inspect): the 83
`Certificate` rows and their parent `Application` rows **remain in the
database**, but every value in the 12 dropped columns is destroyed,
specifically for each of the 83 imported rows:

- **`verificationToken`** — the opaque per-issuance QR token for the 78
  non-held records. **Lost permanently.** Any already-printed QR code or
  PDF for these 78 buyers becomes permanently unscannable — the token it
  encodes no longer exists anywhere once the column is dropped.
- **`isPubliclyBlocked` / `publicBlockReason`** — the hold flag and
  human-readable reason for the 5 held records. **Lost.** Nothing in the
  remaining `certificate` row indicates these 5 were ever held or why.
- **`buyerDisplayName`, `county`, `locality`** — the only place the
  buyer's name and location are recorded for historical-import rows
  (`Application.data` only has a generic `buyer.fullName`/`buyer.county`
  sub-object, not maintained at the same fidelity as the dedicated
  columns, and locality has no equivalent anywhere else). **Lost.**
- **`sourceRecordId`** — the idempotency key matching each row back to its
  row in the source register. **Lost — this is the most consequential
  loss**, detailed below.
- **`stagedPermitNumber`** — the original conflicting permit number for
  the 2 held records that lost the UNIQUE `certificateNumber` slot to
  their counterpart. **Lost.**
- **`isHistoricalImport`, `importRawData`** — the flag distinguishing a
  backfilled record from a live CMIS approval, and the verbatim
  source-register audit snapshot (raw county string, raw date labels,
  flags). **Lost.**
- **`predecessorCertificateId`, `agencyCertificateId`** — not populated by
  the historical import (both null for every imported row today), so
  nothing is lost here *for this specific import*, but any renewal/agency
  link made through the admin UI after go-live would be lost the same way.

After the column drop, what's left on each of the 83 surviving
`Certificate` rows is only the pre-existing fields:
`certificateNumber`/`stagedPermitNumber`-holder (null for the 2 that had
only a staged number), `permitOrLicenceType = "LOCAL_BUYER"`, `issueDate`,
`expiryDate`, and timestamps — indistinguishable from any other
certificate row, with no way to tell it came from this import or who the
buyer was without the dropped columns.

### The re-import duplication risk (tested, confirmed)

This is the critical risk a reviewer must understand before ever running
`down.sql` in an environment where the import has already been applied:

**If `up.sql` is re-run and the import is applied again after a rollback,
it does NOT resume cleanly — it is no longer idempotent, because its only
idempotency key (`sourceRecordId`) was wiped by the rollback.**

Tested directly: apply import (83 rows) → `down.sql` → `up.sql` again →
apply import again. Result:
- Certificate table went from 83 rows to **166 rows** (83 old orphaned
  rows + 83 newly-created rows for the same 83 people).
- Every old orphaned row still holds its original `certificateNumber`
  (since that column/constraint was never touched by the rollback), so
  every **new** re-imported row for the same buyer collides with the
  UNIQUE constraint and is silently assigned `stagedPermitNumber` instead
  of `certificateNumber` — **even for buyers who were never held or in
  conflict in the original import.**
- Worse: these newly-misrouted rows are **not marked `isPubliclyBlocked`**
  (the conflict-detection logic only flags true shared-number conflicts
  from the source data itself, not accidental collisions with
  now-anonymous leftover rows) — yet they **do** get a fresh
  `verificationToken` and so a live, publicly-scannable QR. Scanning that
  QR would call `toPublicPermitView()`, which reads
  `certificate.certificateNumber` as the public `permitNumber` field —
  **returning an empty/null permit number to the public**, for a
  non-held, "valid"-looking record. This was confirmed directly in testing
  (A. Quiah Nelson's re-imported row: `certificateNumber = NULL`,
  `stagedPermitNumber = 'LACRA-194-2026'`, `isPubliclyBlocked = false`,
  has a live token).
- The 83 old orphaned rows remain in the database indefinitely with no
  buyer name, county, or any other identifying data (all dropped), and no
  flag distinguishing them from a normal certificate.

**Conclusion: `down.sql` must never be run in any environment after the
historical import has been applied, except as the first step of a
deliberate, fully-reviewed data cleanup (see restore procedure below) —
never as a routine "undo the migration" action.** This is now also
enforced in code — see Guard 1 above.

### Held records remain blocked throughout — confirmed

Because Guard 1 makes `down.sql` abort before any statement takes effect,
the held records' `isPubliclyBlocked = true` flag, their
`verificationToken = NULL` state, and the guard logic in both public
routes are **never altered by a rollback attempt** — there is no window
during which a held record becomes more exposed than before the attempt.
This was confirmed directly: immediately after a (correctly-refused)
`down.sql` run against a disposable database holding all 83 imported
records (5 held), both public routes' guard logic was checked against all
5 held records and all 5 remained correctly blocked (both the
token-route and the certificateNumber-route return their standard
"not found" response for every one of them), with their underlying data
completely unchanged by the aborted rollback attempt.

Put another way: in the current design there is no partial/in-progress
rollback state to protect against — Guard 1 makes the operation
all-or-nothing at the transaction level, and it always resolves to
"nothing," so held records are never at risk *during* a rollback attempt
in the first place.

### How to restore the lost values if rollback is ever needed after the import

If `down.sql` must be run after the import has already been applied (e.g.
to fully back out this feature), do NOT simply re-run `up.sql` + the
import afterward per the risk above. Instead:

1. **Before running `down.sql`**, export the full set of dropped-column
   values for the 83 (or however many exist at that time) Local Produce
   Buyer certificate rows:
   ```sql
   COPY (
     SELECT id, "verificationToken", "buyerDisplayName", county, locality,
            "predecessorCertificateId", "agencyCertificateId",
            "isPubliclyBlocked", "publicBlockReason", "stagedPermitNumber",
            "sourceRecordId", "isHistoricalImport", "importRawData"
     FROM certificate
     WHERE "permitOrLicenceType" = 'LOCAL_BUYER'
   ) TO '/path/to/backup/local_produce_buyer_columns_backup.csv' WITH CSV HEADER;
   ```
   (A full `pg_dump` of just the `certificate` table, or a full database
   backup taken immediately before rollback, achieves the same result and
   is the simpler option if available.)
2. Run `down.sql`.
3. If the feature is later reinstated, run `up.sql` again (safe —
   `IF NOT EXISTS` guards throughout), then **restore the exported values
   by matching on `id`** (the `Certificate` primary key, which is
   untouched by `down.sql`/`up.sql` — only the 12 feature-specific columns
   are added/dropped, never the row itself):
   ```sql
   UPDATE certificate c SET
     "verificationToken" = b."verificationToken",
     "buyerDisplayName" = b."buyerDisplayName",
     county = b.county,
     locality = b.locality,
     "predecessorCertificateId" = b."predecessorCertificateId",
     "agencyCertificateId" = b."agencyCertificateId",
     "isPubliclyBlocked" = b."isPubliclyBlocked",
     "publicBlockReason" = b."publicBlockReason",
     "stagedPermitNumber" = b."stagedPermitNumber",
     "sourceRecordId" = b."sourceRecordId",
     "isHistoricalImport" = b."isHistoricalImport",
     "importRawData" = b."importRawData"
   FROM backup_table b
   WHERE c.id = b.id;
   ```
   This is a restore from an explicit backup, not a re-import — it is the
   only approach that avoids the duplication risk above, since it never
   calls `LocalProduceBuyerImportService.apply()` against an already-populated
   but idempotency-key-stripped table.
4. **Do not attempt to re-derive `sourceRecordId`, `verificationToken`, or
   `importRawData` from any other table** — none of that data exists
   anywhere else in the schema once the columns are dropped; the backup
   from step 1 is the only recovery path.

This restore procedure was not executed against a live test in this phase
(it requires a pre-existing backup file to restore from, which only
exists once a real rollback has actually happened) — it is a documented,
reviewed procedure for staff to follow if rollback after import is ever
genuinely needed, derived directly from the column list `down.sql` drops
and the `id`-stability guarantee both SQL files preserve.

## Two additional pre-release confirmations

Two specific edge cases were raised before approving a push, and both were
tested directly against a fresh disposable database (schema +
83-record import applied, `DB_SYNCHRONIZE=false`):

### Confirmation 1 — a legitimate office-assisted application does not trigger the orphaned-import guard

**Concern:** Guard 2 (`assertNoOrphanedImports`) flags `LOCAL_BUYER`
certificates with no `sourceRecordId`. A live, office-assisted Local
Produce Buyer application (staff entering a walk-in applicant's permit
through the normal `/apply` workflow, not the historical importer) also
has no `sourceRecordId` by design — it must not be mistaken for an
orphaned/corrupted import row.

**Why it's safe:** the guard does not key on "no `sourceRecordId`" alone —
it requires **both** no `sourceRecordId` **and**
`Application.submissionMethod = "Historical Register Import"` (the value
only the importer ever sets, at
`LocalProduceBuyerImportService.ts` line ~321). A live office-assisted
application's `submissionMethod` is set by `ApplicationController.ts`
line 239 to `"Entered by Commercial"` for the `OFFICE_ASSISTED` channel
(and `"Self-Service"` for `ONLINE`) — never `"Historical Register
Import"`. The two signals are mutually exclusive by construction, so a
live application can never match the guard's condition.

**Tested:** against a disposable DB already holding the 83 imported
records, created one additional `Certificate` row with
`permitOrLicenceType = "LOCAL_BUYER"`, `sourceRecordId = NULL`, and its
parent `Application.submissionMethod = "Entered by Commercial"` —
reproducing exactly what `dgApproveFinal()` + a future `printCertificate()`
step would leave for a real walk-in buyer's permit. Then called both
`preview()` and `apply()`:
- `preview()` completed normally (`matched: 83, added: 0, conflict: 0`) —
  **did not throw**.
- `apply()` completed normally (`matched: 83, added: 0`) — **did not
  throw**, and made no unwanted writes (certificate count correctly stayed
  at 84 — the 83 imported + the 1 new live record — before and after).

**Result: PASS.** The guard correctly ignores legitimate live
office-assisted (and online self-service) applications and only fires on
rows that carry the importer's own provenance marker.

### Confirmation 2 — held permits stay blocked if application code is rolled back but the schema stays in place

**Concern:** if a future deploy rolls back the *application code* (e.g.
reverting to a version before this phase's guards existed) while leaving
the *database schema and data* untouched, held/blocked permits must still
not become publicly resolvable.

**Why it's safe:** `isPubliclyBlocked` is a **data column**, populated
once at import time (or whenever a record is later flagged), not a value
the application computes at read time. The guard condition in both public
routes checks this stored column directly
(`certificate.isPubliclyBlocked`) — a pre-existing check that predates
this phase and was never modified, only supplemented by the new
`hasIssuedPermitNumber()` check. A code rollback to the version before
this phase would still carry that original `isPubliclyBlocked` check
forward, because it is not part of what this phase changed.

**Tested:** against the disposable DB from Confirmation 1 (83 imported
records, 5 held, schema with all 12 Local Produce Buyer columns intact —
i.e. no `down.sql` involved in this check at all, exactly matching "code
rolled back, schema stays in place"):
- Confirmed all 5 held records have `isPubliclyBlocked = true` in the
  data itself, independent of any application code.
- For the 3 held records that have a real `certificateNumber` on file
  (the 3 true "shared number" conflicts, as opposed to the 2 that only
  have a `stagedPermitNumber`), called
  `ApplicationController.verifyCertificate()` with that real
  certificate number — **all 3 correctly returned 404**, despite a
  genuine, matching `certificateNumber` existing in the table.
- None of the 5 held records have a `verificationToken` (by design — no
  QR is ever generated for a held record), so there is no token for the
  public to scan via `verifyByToken()` in the first place; this was
  confirmed directly against the data.
- Additionally confirmed the **pre-existing guard alone** (just
  `isPubliclyBlocked`, without this phase's `hasIssuedPermitNumber()`
  addition) independently blocks all 5 records — i.e. even hypothetically
  rolling back this entire phase's code changes while keeping the schema
  and data as they are today would not expose any held record, because
  the original blocking mechanism was never removed or weakened by this
  phase, only added to.

**Result: PASS.** Held records remain correctly blocked under both the
current code and the pre-existing (pre-this-phase) guard alone, because
the block is enforced by a stored data flag the application reads, not by
logic that a code rollback could silently remove.
