# 2029 — Agency Register

**Status: PROPOSED FOR REVIEW. NOT applied to production.**

## What this migration does
Adds the schema needed for the Agency Register feature (Agencies, with
required Agent/Clerk staffing, under Licensing & Permits):

- 2 new nullable/default columns on `certificate` (`staffingFlagged`,
  `staffingFlagReason`) — additive only. An Agency's own permit record is
  a regular `certificate` row with `permitOrLicenceType = 'AGENCY'`,
  reusing every column the 2028 Local Produce Buyer migration already
  added (`verificationToken`, `buyerDisplayName`, `county`,
  `isPubliclyBlocked`, `publicBlockReason`, `stagedPermitNumber`,
  `sourceRecordId`, `isHistoricalImport`, `importRawData`,
  `agencyCertificateId`) — no new column was needed for those.
- Two new Postgres enum types (`agent_personnel_role_enum`:
  AGENT/CLERK; `agent_personnel_status_enum`: ACTIVE/INACTIVE/REPLACED).
- Two new tables: `agent_personnel` (one row per Agent or Clerk staffed
  at an Agency — see `src/entities/AgentPersonnel.ts` for full field
  documentation) and `agency_import_run` (audit trail of every
  preview/apply import run, mirroring `local_produce_buyer_import_run`).
- No existing column is altered or dropped; all existing rows remain
  valid with the two new `certificate` columns at their defaults
  (`staffingFlagged = false`, `staffingFlagReason = NULL`).

This file was generated by diffing the schema TypeORM's `synchronize: true`
produced on a **disposable copy** of the local staging database
(`eudr_db_agency_staging`, created via `createdb -T eudr_db`) against the
pre-migration schema — `DB_SYNCHRONIZE=false` was set before this file
itself was tested against that copy, so the real `eudr_db` staging
database was never auto-synchronized by this feature's development.

## What this migration deliberately does NOT do
- It does **not** run the 11-Agency / 7-historical-Agent import. That is
  a separate, explicit, idempotent, ADMIN-only application action
  (`AgencyImportService.apply()` / `POST /api/agencies/import/apply`),
  gated on staff reviewing the dry-run reconciliation report first —
  exactly the same review gate used for the 2028 Local Produce Buyer
  import. Folding the import into a schema migration would remove that
  review step.
- It does not touch any table/column outside this feature's scope.
- It does **not** add a renewal workflow for ANY application category.
  `AgencyStaffingService.assertWizardStaffingMet()` is written and ready
  to be called from a future renewal endpoint (per spec: the staffing
  requirement must be enforced "before approving, issuing, or renewing"
  an Agency permit), but no renewal endpoint exists anywhere in this
  codebase today for any category — `predecessorCertificateId` and
  `Application.data.step1.isRenewal`/`previousNumber` remain passive
  display-only fields. Building a renewal endpoint is an explicitly
  deferred follow-up, tracked separately from this migration and from the
  Agency Register's current scope. The staffing check's wizard-level
  function (`validateWizardStaffing`) and the certificate-level function
  (`computeAgencyStaffing`) are both already unit-testable and ready to be
  wired into that endpoint without any schema change when it is built.

## Migration test results (staging, disposable copy)

Tested against `eudr_db_agency_staging`, a `createdb -T eudr_db` copy of
the real local staging database taken immediately before this migration
was applied (so it started from the exact same state: 83 ISSUED
LOCAL_BUYER applications, 1 ISSUED AGENCY application — "Sunrise Trading
Agency", `LACRA-CERT-2026-000002` — and 1 AWAITING_APPLICANT_PAYMENT
LOCAL_EXPORTER application). `DB_SYNCHRONIZE=false` was set for every
command below; schema changes came ONLY from running this `up.sql` file.

1. `up.sql` applied cleanly 3 consecutive times in a row against a freshly
   `createdb -T eudr_db` copy — all `IF NOT EXISTS`/`DO $$` guards confirmed
   safely re-runnable (2nd/3rd runs produced only informational NOTICEs,
   zero errors). **CONFIRMED.**
2. Historical import **preview** (`AgencyImportService.preview()`), run via
   a disposable direct-service-call script against the untouched copy
   (zero rows in `agent_personnel`/`agency_import_run` beforehand),
   reported — **CONFIRMED against actual output, run twice for consistency**:
   - `totalAgencySourceRecords: 11`, `addedAgencyCount: 9`,
     `conflictAgencyCount: 2` (permits `LACRA-AGN-030-2026` and
     `LACRA-AGN-041-2026`), `matchedAgencyCount: 0`.
   - `totalPersonnelSourceRecords: 7`, `addedPersonnelCount: 7`,
     `matchedPersonnelCount: 0`.
   - Sunrise Trading Agency's existing certificate (`LACRA-CERT-2026-000002`,
     looked up directly since it predates/bypassed the printCertificate
     flow and so has a null `buyerDisplayName`) was confirmed untouched:
     `sourceRecordId: null`, `isHistoricalImport: false`,
     `legalNameFromApplication: "Sunrise Trading Agency"` — it was never
     read, matched, or modified by the preview (which only ever matches
     on `sourceRecordId`, and Sunrise Trading Agency has none).
   - Both preview calls were correctly recorded in `agency_import_run`
     with `isDryRun: true` and the counts above.
3. Historical import **apply** — **CONFIRMED.** Run once against the
   post-preview copy (still 1 pre-existing AGENCY cert, 0 `agent_personnel`
   rows beforehand): created exactly 9 new ADDED `application`+`certificate`
   pairs (status `ISSUED`, `submissionMethod = "Historical Register Import"`)
   plus 2 more application+certificate pairs for the 2 CONFLICT permits
   (030/041 — held via `isPubliclyBlocked: true`, `certificateNumber` left
   null, `stagedPermitNumber` set instead) — 11 new AGENCY applications
   total, all status `ISSUED` — and 7 new `agent_personnel` rows. Counts
   after: 12 AGENCY certs (1 pre-existing + 11 imported), 7 personnel rows.
   Re-running **apply** a second time against the same database reported
   `matchedAgencyCount: 11`, `addedAgencyCount: 0`, `conflictAgencyCount: 0`,
   `matchedPersonnelCount: 7`, `addedPersonnelCount: 0` — confirmed
   idempotent; counts after run 2 were unchanged (still 12 / 7) — **no
   duplicate rows created.** The 3 personnel records with no candidate
   parent Agency (`LACRA-AGENT-HIST-003` Ousmane Sow, `-006` Larry Clark,
   `-007` Sekou K. Sheriff — all `requiresAgencyConfirmation: true`) were
   confirmed to have `agencyCertificateId: null` after both runs — they
   remain unlinked, not guessed into any Agency. All 11 imported Agencies
   came out `staffingFlagged: true` (0-1 of 3 required Agents, 0 of 1
   required Clerk — expected, since `confirmedClerks` is empty in the
   source package) with a `staffingFlagReason` explicitly stating "the
   Agency's issued permit status is unaffected" — and all 11 `application`
   rows were confirmed to remain `status = ISSUED` throughout (staffing
   flags never altered permit status). Sunrise Trading Agency's
   certificate (`LACRA-CERT-2026-000002`) was re-checked after both apply
   runs and confirmed unchanged (`sourceRecordId: null`,
   `isHistoricalImport: false`).
4. Staffing-requirement enforcement + public-verification demonstrations —
   **CONFIRMED**, run via direct service-layer calls (no frontend exists
   yet; the gate/service functions themselves are what was exercised):
   - `assertWizardStaffingMet()` (the exact function wired into
     `dgApproveFinal`/`printCertificate`): 2 Agents + 1 Clerk ->
     **BLOCKED**, throwing `AgencyStaffingRequirementError` with message
     "at least 3 distinct active Agents and exactly 1 active Clerk are
     required. Currently registered: 2 agent(s), 1 clerk(s)." 3 Agents + 1
     Clerk -> **PASSED**. 4 Agents + 1 Clerk -> **PASSED**. Confirms the
     "3 OR 4 distinct active Agents + exactly 1 active Clerk" requirement.
   - Incomplete draft save: a `DRAFT`-status Application with only 1
     Agent and no Clerk was created and persisted successfully (the
     staffing gate is only ever invoked at DG-approval/issuance time, never
     at draft save) — confirms staff can save an incomplete draft.
   - Shared permit / distinct QR: two new Agents appointed under the same
     already-issued Agency (`LACRA-AGN-001-2026`, Konmana Cocoa Corporation
     Inc.) both carry `permitNumber = "LACRA-AGN-001-2026"` but got two
     distinct, randomly-generated `verificationToken` UUIDs — confirmed
     both resolve independently via `computeAgentPublicStatus()`/
     `toPublicAgentView()` (both `VALID` while both ACTIVE).
   - Deactivation: one of those two Agents was set to `INACTIVE` — its
     `computeAgentPublicStatus()` result changed from `VALID` to
     `AGENT_NOT_ACTIVE` immediately, while the other (still-ACTIVE) Agent
     remained `VALID` — confirms a deactivated Agent's QR no longer
     verifies them as authorized, without affecting the Agency or other
     Agents.
   - Held records: the real imported conflict Agency `LACRA-AGN-030-2026`
     (ID Cocoa Incorporated) has `isPubliclyBlocked: true`,
     `verificationToken: null`, `certificateNumber: null` — so
     `GET /api/public/agencies/verify/:token` has no token to even match
     against (always 404 by construction, not just by a runtime check).
     The Agent historically imported under it (T. Abraham Browne) is
     likewise `isPubliclyBlocked: true` with `verificationToken: null` —
     confirms held records (both Agency- and Agent-level) stay blocked
     from public verification.
   - All disposable demo rows (2 appended Agents, 2 throwaway test
     Applications) created solely for this demonstration were deleted
     from `eudr_db_agency_staging` immediately afterward; final counts
     (12 AGENCY certs, 7 `agent_personnel` rows) match the post-apply
     state exactly, confirming no demo data was left behind.
